# パフォーマンス最適化の進め方（設計思想と判断軸）

新規プロジェクト・既存プロジェクトいずれでも、リリース前のパフォーマンス改善フェーズで読み返すための文書。コードのコピペ集ではなく、**「なぜ・どこで・どう判断したか」** の記録。

## 読み方

- 各層の **役割と境界** を理解する。具体ライブラリ名やコードは観点を支えるための例示
- 「**やらない判断のセクション**」が一番効く部分。実装した量より判断した量で品質が決まる

---

## 設計思想

### 思想1: 計測駆動（Measure-Driven）

**「推測で最適化しない、計測で判明したボトルネックだけ直す」**

- 開発者の直感が当たるのは半分以下。経験的に重そうな箇所と実際の P95 が一致しないことが多い
- 「明らかに遅いはず」も計測すると順位が下位、ということはよく起きる
- ボトルネックの 80% は上位 5 件の API / クエリ / 画面に集中する → 残りは触らなくて良い

実務的には **層1（計測基盤）を最優先で整える**。計測なしの最適化は、効果不明・回帰リスク・PR 肥大化の三重苦になる。

### 思想2: 現状調査優先

**「計画通りに実装する前に、既に達成されているか確認する」**

過去フェーズで似た作業がされていることが多い。新規プロジェクトでも、フレームワーク・ライブラリのデフォルトで既に最適化されている項目がある。

- 計画 = 「あるべき状態」の記述
- 実装 = 「現状とあるべきのギャップ」を埋める作業
- 既にあるべき状態なら、実装は不要

「やった感」のために重複作業を入れると、PR が膨らみレビュー負荷が上がる。**判断した結果として実装量が減るのは成功**。

### 思想3: YAGNI（You Aren't Gonna Need It）

**「使われない抽象・プリセット・ヘルパは作らない」**

計画書に書いてあっても、実コード上で 1 箇所も呼ばれないなら不要。「将来便利かも」で残すと：

- 改修時に解読コストが発生する
- 別の人が「これは使うものだ」と誤認して新規箇所で使う（劣化版が増える）
- リネーム・削除が機械的にできなくなる

`@CacheKey` デコレータ、汎用 `SelectResult<Model, Select>` ヘルパ、すべてのモデル用 `*_PUBLIC_SELECT` プリセットなど、**「網羅的に作っておきました」型の抽象は特に YAGNI 違反になりやすい**。

### 思想4: Fail-Open（フェイルオープン）

**「最適化レイヤが落ちても、アプリ全体は動き続ける」**

キャッシュ・CDN・圧縮ミドルウェア・ログ転送のような **最適化レイヤ** は、それ自体が単一障害点になりやすい。例外を飲んで本来の処理（DB クエリ・通常レスポンス）に fallback する設計が安全。

逆に **認可・バリデーション・トランザクション** は fail-closed（失敗時は処理を止める）で、最適化レイヤとは判断が逆になる。

### 思想5: 「やらない判断」を記録する

「やった」より「**やらなかった理由**」のほうがあとで効く。

- レビュアーが「なぜ計画と違うのか」を聞いてきた時の答えになる
- 半年後の自分が「この最適化、やってなかったっけ？」と再度検討する時の参照になる
- 別プロジェクトに知見を持ち込む時に、判断基準ごと持って行ける

PR 説明・コミットメッセージ・ナレッジドキュメントのいずれかに必ず残す。

## 全体構成: 5層 + 計測基盤

```
                ┌──────────────────────────────────────────┐
                │  層1: 計測基盤（measurement foundation）  │
                │   ・サーバ側スロー閾値ログ                │
                │   ・Sentry / APM Trace                    │
                │   ・バンドルサイズ可視化                  │
                │   ・Lighthouse CI                         │
                │   ・ベースライン文書化                    │
                └──────┬───────────────────────────────────┘
                       │ 計測値が次の層の対象を決める
                       ▼
┌──────────────────────┐  ┌──────────────────────┐
│  層2: バックエンド DB  │  │  層4: フロントエンド  │
│   ・select / projection │  │   ・コード分割（dynamic import）│
│   ・SQL 集計化（N+1解消）│  │   ・画像最適化（next/image 等）│
│   ・インデックス確認    │  │   ・戦略的メモ化       │
│   ・並列化制限         │  │   ・SSR/RSC レビュー   │
│   ・開発時クエリログ    │  │                      │
└──────────┬───────────┘  └──────────┬───────────┘
           │                         │
           ▼                         ▼
┌──────────────────────┐  ┌──────────────────────┐
│  層3: キャッシュ層     │  │  層5: ネットワーク    │
│   ・マスタデータ TTL   │  │   ・gzip / brotli 圧縮│
│   ・集計値 TTL         │  │   ・Cache-Control     │
│   ・公開上位リスト TTL │  │   ・ペイロード最小化   │
│   ・write 時 invalidate │  │   ・pagination 上限    │
│   ・fail-open          │  │   ・client query       │
│                      │  │     staleTime          │
└──────────────────────┘  └──────────────────────┘
```

順序のポイント：

- **層1 が最優先**（計測なしの最適化は迷走する）
- 層2 / 層4 は計測結果に応じて並行可能
- 層3 と 層5 は層2 / 層4 の延長で効果が出やすい
- 層3 と 層5 はネットワーク経路を変えるので、最後に動作確認の手間を集める方が良い

## 層1: 計測基盤

### 観点

- **「数字で語れるベースライン」を最初に作る**。Before/After を数値で示せないと改善の合意が取れない
- **本番計測 / CI 計測 / ローカル計測** で見えるものが違う。最低 2 つ揃えるのが現実解

### サーバ側スローログ

リクエスト処理時間を **JSON 構造化ログ** で常時記録。閾値（例: 1 秒）超を `slow request` のような固有キーワードで強調マーク → grep / 集約ツールで容易に抽出。

| ライブラリ候補              | 言語 / フレームワーク      |
| --------------------------- | -------------------------- |
| `pino-http` / `nestjs-pino` | Node.js / NestJS / Fastify |
| 標準ロガー + middleware     | Express / Koa              |
| 標準 `slog` + middleware    | Go                         |
| `structlog` + middleware    | Python                     |

閾値の決め方：

- 1 秒 → 体感「ちょっと遅い」のライン、ノイズもある程度出る
- 3 秒 → 体感「壊れてる？」のライン
- 100ms → API のテーブル取得程度の典型値、ここを超えるのを情報レベルでマーク

### APM / Sentry Trace

サンプリング率は **常時 0.1〜0.2 程度**、ボトルネック調査期間のみ 1.0 に上げる運用が定石。常時 1.0 はコストとレポート量が爆発する。

### バンドル分析

クライアントサイドバンドルは treemap で可視化する。`@next/bundle-analyzer` / `webpack-bundle-analyzer` / Vite の `rollup-plugin-visualizer` 等。

「**重いライブラリ X が想定外のページに含まれている**」が高頻度の発見。動画プレイヤー / リッチエディタ / グラフライブラリは典型的に動的 import 候補。

### Lighthouse CI

**main ブランチへのマージ時のみ** 実行が現実解：

- PR ごと実行は CI 時間が膨らむ + ネットワークノイズで結果が揺れる
- main マージ時に時系列スコアを残すと「徐々に劣化していく」が見える

閾値設計：

- Performance < 80 → warn（マージブロックしない）
- Accessibility < 90 → error（コントラスト・aria など機械的に直せる）

### ベースライン文書化

**改善前の数値を専用 md に記録する**。改善後に同じ手順で再測定し、Before/After を並べる。手順も書いておけば誰でも再現できる。

### よくある「先に計測したら別の問題が見つかる」例

- ビルドが本番モードで通らない（共通 layout で外部 fetch をして SSG タイムアウト 等）
- 本番ビルドだけで起きる SSR エラー（Server Components で cookies / headers 呼びを忘れている）
- バンドルに dev 専用ライブラリが入っている

これらは **計測しようとした副作用で発見される**。発見次第、計測の前提条件として直す（独立タスク化）。

## 層2: バックエンド DB 最適化

### 観点

- **転送量・メモリ使用量・SQL 実行回数** の3つを減らす
- リレーション JOIN の代わりに **必要フィールドのみ projection**（select / specific columns）
- ループ内 DB 呼び出しは **ループ前に一括取得 + Map** で N+1 を解消
- 「メモリで集計」より「**DB で集計**」が定数倍以上速い（COUNT, GROUP BY, MAX 等）

### projection（select / 列指定）の徹底

ORM の `include` / `with` のような「全フィールド取得」は機密漏洩リスクと転送量肥大の両方を生む：

- `passwordHash` のような **絶対に出さないフィールド** が、view 層で誤って JSON 化される事故
- レスポンスサイズが本来必要な分の 2〜5 倍に膨らむ

**典型的に最初に直すべきは User / Account 系の取得**。安全な公開フィールドだけを集めたプリセットを 1 箇所に置き、各所で参照する。

### N+1 の解消パターン

```
NG:  for each record { fetch related; ... }       // ループ内 fetch
OK:  fetch all related WHERE id IN (...);
     map = new Map(...);
     for each record { related = map.get(...); }
```

これは ORM・言語問わず汎用的に適用可能。**`.map(async ...)` + `Promise.all` でも N+1 になることに注意**（並列にはなるが N 個のクエリは飛ぶ）。

### SQL 集計化

```
NG:  records = SELECT * FROM ... WHERE ...        // 全件メモリロード
     for each record { count + 1 }                // JS で集計
OK:  SELECT status, COUNT(*) FROM ... GROUP BY status
```

`groupBy({ by: ['status'], _count: { _all: true } })` のような ORM API を使えば SQL を直接書かずに済む。複数の groupBy を並列実行（`Promise.all`）にするとさらに早い。

### インデックス確認

スロークエリが見つかったら `EXPLAIN ANALYZE` を見る。`Seq Scan` が出ていれば WHERE / ORDER BY のカラムにインデックスが必要。**新規インデックスは個別マイグレーション** で追加する（適用順序が読みやすい）。

### 並列度制限（p-limit / semaphore 等）

メール一括送信のような外部 API 呼び出しを並列化する時は、**並列度に上限**（10〜20 程度）を設ける。`Promise.all([...1000])` だと API のレート制限・接続プール枯渇で逆に遅くなる。

ただし **対象が未実装（mock 状態）の段階では並列化を入れない**。実装と並列化は同時にやる方がレビューしやすい。

### 開発時クエリログ

ORM の log オプションで開発環境のみ全クエリを stdout に流す。`emit: "event"` で購読する形なら duration を含めたカスタムフォーマットが書ける（100ms 超を `[~100ms]` でマーク等）。

開発中に画面遷移しながら **コンソールに連続で同じ SELECT が出ていれば即 N+1** と分かる。

## 層3: キャッシュ層

### 観点

- **更新頻度低 × 参照頻度高** のデータを Redis などに置く
- **書き込み時に invalidate** するか、**TTL のみで失効** に割り切るかを決める
- **Fail-open**: キャッシュ層が落ちても DB から取得して返す

### キャッシュする / しないの判断

| 適性高                                     | 適性低                                           |
| ------------------------------------------ | ------------------------------------------------ |
| マスタデータ（カテゴリ・ランク・機能設定） | ユーザー固有データ（通知一覧・マイページ）       |
| 集計値（ダッシュボード・ランキング）       | リアルタイム性が要るデータ（チャット・最新投稿） |
| 公開上位リスト（おすすめ・人気）           | 個人化要素を多く含むレスポンス                   |

ユーザー固有データは **キーが大量に増える** ＋ **invalidate のタイミングが複雑** になりやすい。基本対象外で、本当に効果がある時だけ個別に検討。

### 自前実装 vs 既製ライブラリ

**必要 API が `getOrSet / invalidate` の 2 つだけ** なら、ioredis や node-redis を直接ラップする 30〜50 行の自前実装で十分。利点：

- バージョン互換問題（peer dependency など）から自由
- 何が動いているか完全に見える
- 余計な機能（タグ付き invalidate / 階層キャッシュ等）の誘惑がない

`@nestjs/cache-manager` 等の既製ライブラリは複雑度が増えた時に検討。

### キャッシュキー設計

**`prefix:scope:key` 形式で統一**：

```
master:feature-settings:all
master:member-ranks:all
stats:dashboard
events:featured
events:detail:{id}
```

`invalidate("events:")` で `events:*` を SCAN + UNLINK 一括削除できる構造にしておく。

### 環境別 prefix

dev / staging / prod が **同じ Redis を共有する可能性** に備えて、すべてのキーに環境名 prefix を自動付与（`prod:master:...`）。dev データが prod に漏れる事故を防ぐ。

### `KEYS *` は本番禁止

`KEYS pattern` は **全キーをブロッキングで列挙する** ため、Redis に大量データがあると数秒〜数十秒のフリーズを引き起こす。**`SCAN` を使う**（カーソルベースで非ブロッキング）。

削除も `DEL` ではなく **`UNLINK`**（バックグラウンド削除、応答即時返却）が安全。

### TTL 方針の例

| データ種別                 | TTL    | 理由                                              |
| -------------------------- | ------ | ------------------------------------------------- |
| マスタ（更新頻度: 月数回） | 1 時間 | 即時反映の必要なし、admin 更新後 1 時間以内に反映 |
| 集計値（ダッシュボード）   | 10 分  | 重い集計、即時性不要                              |
| 公開上位リスト             | 5 分   | 新着の反映と高速化のバランス                      |

短すぎ → キャッシュ効果なし、長すぎ → 古いデータ。**書き込み invalidate を併用**するなら長め、TTL のみなら短めが目安。

### invalidate vs TTL のみ の選択

- **書き込みトリガーが特定できる**（マスタの create/update/delete 等）→ invalidate を呼ぶ。TTL は保険として長めに
- **書き込みトリガーが多すぎる**（集計値、ランキング、横断的な数値）→ TTL のみで失効させる。書き込み箇所すべてに invalidate を仕込むと結合度が爆発する

### Fail-open の徹底

```
読み:  Redis 取得で例外 → factory（DB 取得）に fallback
書き:  Redis SET で例外 → 警告ログを出して結果は返す
```

キャッシュ層の障害でアプリが止まる設計は危険。「**あれば速い、なくても動く**」が鉄則。

## 層4: フロントエンド最適化

### 観点

- **初回読み込み速度（First Load JS）** を減らす
- **画像 / 画面表示** をブラウザ標準の最適化に任せる
- **再レンダリング頻度の高い箇所のみ** メモ化する（全箇所メモ化は逆効果）

### コード分割（動的 import）

バンドル分析で **重い依存（数百 KB レベル）** が特定のページでしか使われないなら、`next/dynamic` / `React.lazy` 等で遅延ロード化：

```
通常 import: そのページの初期バンドルに同梱
動的 import: 必要になった瞬間に別 chunk として取得
```

典型的な候補：

- 動画プレイヤー（HLS.js 等、~150KB gzip）
- リッチテキストエディタ（TipTap, Slate 等）
- グラフライブラリ（Recharts, Chart.js 等）
- カレンダー / 日付ピッカー（FullCalendar 等）
- 絵文字ピッカー

判断基準：**バンドル分析で特定ページの First Load JS の大半を占めている** + **そのライブラリが操作開始時にロードされても UX 上問題ない** の両方を満たすこと。

### Image 最適化

`next/image` のような **フレームワーク標準の Image コンポーネント** を使うことで以下が自動化される：

- viewport 外の画像を **lazy load**
- デバイスサイズに応じた **解像度配信**
- **WebP / AVIF への自動変換**

設定で必要なこと：

- `remotePatterns` で許可ホストを列挙（CSP `img-src` と整合させる）
- `formats` でモダンフォーマットを優先指定
- ファーストビュー画像のみ `priority` 指定（LCP 候補）

`fill` モードを使う場合は親要素に `position: relative` + サイズ確定が必要。`sizes` 属性は必ず設定する（書かないと最大解像度が常に配信される）。

### 戦略的メモ化

`React.memo` / `useMemo` / `useCallback` は **頻繁に再レンダリングされる親の中に多数の子がいる** 場面でだけ効果がある。代表例：

- チャット・通知（外部イベントで頻繁に状態変化）
- 大量リスト（スクロールで再描画頻発）
- テーブル系（ページネーションで局所更新）

**全コンポーネントメモ化は逆効果**：

- 比較コストが付加される
- props の参照が安定していないと結局再計算する
- メモリ消費が増える

メモ化前に **「親で本当に頻繁な再レンダリングが起きているか」** を React DevTools の Profiler で確認するのが先。

### SSR / RSC の使い分け

React Server Components / Next.js App Router では **デフォルトはサーバ側レンダリング**。クライアント機能（state, event, browser API）が必要な箇所のみ `"use client"` を付ける。

不必要に `"use client"` が付いていると：

- そのコンポーネント以下が全部クライアント送信される
- バンドルサイズが膨らむ
- SSR の高速化を活かせない

定期的な audit で減らすが、**バンドル分析で具体的に膨らんでいる箇所が見つかってから**やるのが効率的（YAGNI）。

### フォント最適化

- 標準で `next/font/google` / `next/font/local` のようなフレームワーク機能を使う
- `<link rel="stylesheet" href="https://fonts.googleapis.com/...">` 直接埋め込みは CLS（Cumulative Layout Shift）を悪化させる

これは既存プロジェクトのデフォルト設定で対応済みなことが多いので、新規調査は不要。

## 層5: ネットワーク最適化

### 観点

- **転送量** を圧縮で削る
- **リクエスト回数** をクライアントキャッシュで削る
- **巨大リクエスト** をガードで防ぐ

### 圧縮

JSON は冗長性が高く、gzip / brotli で **60-80% 圧縮** される。サーバ側で `compression` ミドルウェアを 1 行追加するだけ。

CDN 経由なら CDN が圧縮するが、**API 直接アクセス（モバイルアプリ等）に備えてサーバ側でも有効化**しておくのが安全。Cloudflare 等は二重圧縮を避けて Content-Encoding を尊重する。

### HTTP Cache-Control

| 値                   | 用途                                             |
| -------------------- | ------------------------------------------------ |
| `public, max-age=N`  | 全ユーザー共通の公開リソース。CDN もキャッシュ可 |
| `private, max-age=N` | 個人向けだがブラウザキャッシュは可               |
| 何も付けない         | 安全側、毎回 fetch（迷ったらこれ）               |
| `no-store`           | 絶対にキャッシュしない（金融系・PII）            |

**個人化要素ゼロの公開系**（FAQ・公開コンテンツ・ランキング等）に `public` を付けると CDN が数十 ms で返せる。書き込み（POST/PATCH/DELETE）には付けない（GET 以外はそもそもブラウザがキャッシュしない）。

### ペイロード最小化

WebSocket / SSE / API レスポンスで「**必要なフィールドのみ**」送る。チャットメッセージなどは：

- `sender: { ...全プロフィール }` ではなく `senderName + senderAvatarUrl` のフラット化
- ネスト構造を浅くしてバイト数を削る

ただしこれは projection（層2）で既に達成されていることが多い。

### Pagination 上限

`limit=10000` のような巨大リクエストを防ぐ：

- 共通 Pagination DTO に **`@Max(100)` のような上限ガード**
- ハードコード上限 `Math.min(query.limit ?? 20, 100)` で確実化

DTO レベルでガードしておくと、悪意のあるクライアントによる DB 圧迫を防げる。

### クライアント側 staleTime

TanStack Query / SWR / Apollo Client などの **キャッシュ層の `staleTime`** を全体設定する：

- デフォルト 0 だと画面遷移・タブ切替・focus のたびに再 fetch
- 60 秒程度の staleTime を入れると体感が改善 + サーバ負荷軽減

個別の hook で上書きする場合は、**「リアルタイム性が必要な箇所」**（通知・チャット）のみ短く / 0 に設定。

### ETag / Conditional Requests

「変わってないリソースを 304 で返す」最適化は CDN（Cloudflare 等）が自動でやる。**自前実装は CDN 構成決定後** に検討するのが効率的。

## やらない判断 — 計画通りに進めない時の見極め

ここが **このドキュメント全体で一番重要なセクション**。

### 「既に達成されている」を見抜く

新規プロジェクトでも、フレームワーク・ライブラリ・過去のリファクタですでに最適化されていることがある。実装前に必ず：

1. **対象 service / module の現状コードを読む**（grep で直近の実装を確認）
2. **計画の Before パターンに該当するか** チェック
3. **すでに After の形になっていればスキップ**

判断のコツ：

- ループ内 DB 呼び出しが「ある」のではなく「**まだ残っている**」のかを見る
- 全件 fetch が「**実際の API 呼び出しパス上に**」存在するか
- 共通プリセット（`AUTHOR_SELECT` 等）が既に整備されているか

### 「対象が未実装なら今やらない」

以下のような状況では、**計画書に書いてあっても実装を見送る**：

- 並列化対象の処理が `MOCK` ログのみ（実 API 呼び出しがまだない）
- キャッシュ対象の API がまだ実装されていない
- 最適化対象の機能フラグ自体が未着手

実装と最適化は **同じ PR で同時に入れる** 方が、レビュアーが「何を最適化したか」を判断しやすい。

### 「網羅的に作る」より「使われ始めた時に足す」

`USER_PUBLIC_SELECT` / `USER_DETAIL_SELECT` / `USER_INTERNAL_SELECT` のような **「想定される全パターンの抽象」** を先に作るのは典型的 YAGNI。

代わりに：

- 1 つ目の使用箇所が出たら最小限で追加
- 2 つ目で重複が見つかったら共通化
- 3 つ目で抽象が固まる

これが「**Rule of Three**」。先回りで作ると、実コードの実情と乖離した API になりがち。

### 「過剰最適化を避ける」のチェックリスト

実装前に問いかける：

- [ ] このコードは実際に呼ばれているか
- [ ] 計測でボトルネックと判明しているか
- [ ] 既に同等の対策がされていないか
- [ ] 最適化前後で API レスポンス互換性が崩れないか
- [ ] テストで動作保証されているか
- [ ] PR が肥大化していないか（やめる勇気）

すべて Yes なら実装する。1 つでも No なら理由を明文化する（PR 本文 / コミットメッセージ / ナレッジ）。

## 新規プロジェクト適用時のフロー

### Step 1: 計測基盤を整える（層1）

1. サーバ側スローログ
2. APM / Trace の導入（最低限のサンプリング）
3. バンドル分析の有効化（コマンド 1 つで treemap が見られる状態）
4. Lighthouse CI（main マージ時のみ）
5. ベースライン文書化

このステップで **想定外の build / SSG / SSR エラー** が見つかることがある。発見次第、独立タスク化して直す。

### Step 2: ベースラインを取る

- 主要ルートの First Load JS（Web）
- 主要 API の P50 / P95
- バンドル top 10 chunks のサイズと内訳

数値を専用 md に記録する。改善後の比較対象になる。

### Step 3: 対象を特定する

ベースラインから「**実際にボトルネックになっている上位 3〜5 件**」を特定。これだけが最適化対象。網羅的に全箇所最適化はしない。

### Step 4: 各層を順次適用

層2 / 層3 / 層4 / 層5 を、計測結果に応じて適用する。各層内でも：

- まず 1〜2 件でパターンを確立
- 動作確認 + テスト
- 同パターンで残りに展開

### Step 5: After 計測 + 文書化

ベースラインと同じ手順で再測定 → md に Before/After を並べる。**やらなかった項目** も理由付きで記録する。

### Step 6: 別フェーズに送る項目を整理

リリース後・別フェーズで対応する項目をリスト化：

- ETag / Conditional Requests（CDN 構成決定後）
- WebSocket メッセージバッチング（必要時）
- 全 `<img>` の Image 化（段階移行）
- React Compiler（stable 化後）

「**今やらない理由**」を一緒に書くと再検討時に判断しやすい。

## アンチパターン集

| アンチパターン                         | 何が問題か                                   | 代わりに                              |
| -------------------------------------- | -------------------------------------------- | ------------------------------------- |
| 計画書の項目を順に全部実装             | 既に達成済の項目に手を入れて PR 肥大化       | 現状調査 → ギャップのみ実装           |
| 全コンポーネントに React.memo          | 比較コスト + メモリ増                        | Profiler で再レンダリング多い箇所のみ |
| 全 API に `public, max-age`            | 個人化情報が CDN に残るリスク                | 公開系のみ public、個人系は無設定     |
| `Promise.all([...1000])` で並列化      | レート制限・接続プール枯渇                   | 並列度を `p-limit(10)` で制限         |
| `KEYS pattern*` で削除                 | Redis ブロッキング、本番停止                 | `SCAN + UNLINK`                       |
| Cache-Aside の write 側で Redis 再計算 | 失敗時の挙動が複雑                           | 削除のみ。次回 read で再構築          |
| 全 `include` を `select` に置換        | 過剰最適化、リレーション小モデルでは効果なし | User 系・大型レスポンスのみ           |
| キャッシュ TTL なし                    | スキーマ変更時に古いデータが残り続ける       | 必ず TTL を設定（保険）               |
| 推測で「ここが遅そう」と直す           | 真のボトルネックを見逃す                     | 層1 で計測してから                    |
| 計画通り進めなかった理由を書かない     | レビュー・将来の自分が混乱                   | コミット / PR / ナレッジに明文化      |
